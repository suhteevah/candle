**Finding contradicts the commit message claim.** Commit `b8556d7` said
chunked CE "frees ~155 MB logits transient" — actual behavior on
kokonoe at seq=128 is the OPPOSITE: it OOMs an 8GB card that runs the
unchunked baseline cleanly at 7919 MB peak.

### Root cause hypothesis

The chunked CE forward computes loss-on-chunk inside a `while` loop,
each chunk's loss adding to a running `nll_sum` accumulator that
participates in autograd. The graph rooted at the final scaled_loss
holds backward pointers to every chunk's intermediate (logits, log
probs, gather, mask product). Under gradient checkpointing the per-
layer activations drop at layer boundaries, but the CHUNK loss
intermediates persist until backward — so we trade one large transient
that gets freed for N small transients that all stay alive.

At seq=128 with chunk=32 we have 4 chunks producing roughly:
  - logits: [1, 32, 151936] f32 = ~19 MB per chunk
  - log_softmax: same shape = ~19 MB per chunk
  - gather + mask product: ~5 MB per chunk
Total ~43 MB × 4 chunks = ~172 MB extra retained vs single-shot.
Baseline peak 7919 MB on 8192 MB card has ~270 MB driver overhead
margin — adding 172 MB pushes it OOM.

### Actions

1. **Revert** `--ce-chunk-size 32` from `run-matt-voice-overnight.ps1`
   (was added in commit `b8556d7`; matt-voice tonight will OOM at
   step 1 if launched as-is).
2. Mark `--ce-chunk-size > 0` REJECTED at seq=128 on 8GB cards.
3. Re-test at seq=256 / seq=512 where the unchunked logits are larger
   and the savings might outweigh per-chunk retention. Need to add
   those presets to `run-bench.ps1`.
4. File a code-change hypothesis: detach `nll_sum` after each chunk
   so backward has to recompute each chunk's sub-forward via a
   custom-op-style backward; severs the retention chain that's
   currently OOMing us.

### Why the fix didn't work

The per-chunk-backward design is sound — each chunk's backward through
the autograd graph DOES drop after the chunk's `backward_into` returns.
The OOM still happens, so the cause is NOT the autograd retention I
diagnosed at 16:23. Other candidates I haven't ruled out:

1. **cudnn/cublas algorithm cache.** Chunked matmuls have a different
   shape than the single-shot one, and cuBLAS may pick a different
   algorithm with different workspace requirements. The cache could
   hold the workspace alive longer than expected.

2. **lm_head weight pre-dequant interaction.** The 1.1 GB f16 lm_head
   gets matmul'd 4 times instead of 1. The cuBLAS handle's transient
   buffers may not fully release between calls.

3. **GC + chunked backward composition.** Each chunk's backward
   through `narrow(hidden)` deposits a sparse gradient into the
   last-layer-input slot in the checkpoint context. Then
   `backward_through_checkpoints` propagates. Maybe the slot retains
   intermediates between chunk backwards, accumulating instead of
   coalescing.

4. **The single-shot path on 8GB just doesn't have headroom for ANY
   chunked variant.** Baseline peak 7919 MB on 8192 MB card has ~270 MB
   margin; any per-chunk overhead (algorithm cache + extra cuBLAS
   handles + workspace) eats it.

### Real conclusion

**Chunked CE is not deployable on 8GB at seq=128 regardless of the
retention design.** The fix may work on bigger VRAM cards (cnc 16GB
when it's back). Marking the hypothesis CONDITIONAL: re-test on
>=16GB cards.
